# TWINCAP — RONDA 15.2
## CIERRE DEFINITIVO DE INTEGRIDAD FINANCIERA ANTES DE UX/UI

Estamos realizando la **Ronda 15.2 de TwinCap**.

Esta debe ser una **última mini-ronda técnica antes de entrar a la ronda de UX/UI**.

El objetivo NO es simplemente corregir los hallazgos puntuales encontrados después de R15.1.

El objetivo es:

> **dejar la base financiera de TwinCap lo más robusta, coherente, atómica, concurrente, auditable y predecible posible antes de congelar el dominio financiero para UX/UI y beta.**

Por lo tanto, debes trabajar como **ingeniero senior de backend + auditor de integridad financiera**, no como un implementador que simplemente ejecuta una lista de cambios.

# 11. MOVIMIENTOS HUÉRFANOS

Debes definir claramente:

> ¿Cuándo un Movement es considerado huérfano?

Debe distinguirse entre:

### A. Movimiento moderno válido

Tiene un link estructurado y su padre existe.

### B. Movimiento moderno huérfano

Tiene link estructurado pero el padre ya no existe.

### C. Movimiento legacy reconciliable

No tiene link moderno completo pero puede identificarse de manera inequívoca.

### D. Movimiento legacy ambiguo

Existen múltiples candidatos posibles.

### E. Movimiento realmente inválido

No puede ser asociado de forma segura.

# 12. REGLA DE SEGURIDAD PARA LEGACY

Nunca hagas una reparación destructiva cuando exista ambigüedad.

Si hay:

```text
0 candidatos
```

→ huérfano.

Si hay:

```text
1 candidato inequívoco
```

→ reconciliable.

Si hay:

```text
>1 candidato
```

→ ambiguo.

Nunca selecciones arbitrariamente uno.

Nunca borres automáticamente un movimiento ambiguo.

Registra el problema.

# 32. INVARIANTES FINANCIERAS

Crea una lista formal de invariantes.

Como mínimo:

### I1
Todo Movement pertenece a un workspace.

### I2
Todo Movement pertenece a una cuenta válida o está explícitamente clasificado como legacy/orphan según las reglas.

### I3
Todo Movement moderno con `link.kind` válido debe poder resolver su padre vivo.

### I4
Un Movement moderno no debe existir silenciosamente como huérfano.

### I5
Una operación financiera compuesta debe ser atómica.

### I6
Una misma request idempotente no debe crear dos operaciones.

### I7
Una cuenta eliminada no puede recibir nuevas operaciones financieras.

### I8
Una cuenta eliminada no puede ser usada como origen de una nueva operación.

### I9
Una transferencia debe afectar consistentemente sus dos cuentas.

### I10
Los cálculos de saldo deben usar la misma definición de movimiento válido.

### I11
Los movimientos de otro workspace nunca pueden entrar en un saldo.

### I12
Un movimiento ambiguo legacy nunca debe repararse automáticamente.

### I13
Un saldo negativo, cuando esté permitido por el dominio, no constituye por sí mismo un error.

### I14
La advertencia de fondos insuficientes no registra una operación.

### I15
La confirmación posterior registra exactamente una operación.

### I16
Las operaciones multidivisa deben conservar los importes reales de origen y destino.

### I17
El tipo de cambio efectivo debe derivarse de los importes cuando así lo estableció el dominio.

### I18
No debe existir divergencia entre el saldo mostrado y el saldo utilizado para validar una operación.

### I19
Una operación financiera no puede quedar parcialmente aplicada.

### I20
Una referencia cross-workspace debe rechazarse.

Agrega cualquier otra invariante que descubras durante la auditoría.
