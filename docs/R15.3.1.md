# 3. PRIORIDAD ABSOLUTA

Los siguientes tres puntos son **P1 y OBLIGATORIOS**.

## P1.1 — CORREGIR RETRY DEL RATE LIMITER

Audita toda implementación de rate limiting relacionada con MongoDB y verifica especialmente los caminos que manejan errores de índice único.

Actualmente existe riesgo de que el `catch` intente reintentar ante cualquier error de MongoDB.

Esto es incorrecto.

### Regla obligatoria

El retry debe ocurrir **únicamente** cuando el error corresponda realmente a `E11000` / duplicate key y el flujo lo requiera.

Debe quedar:

```text
E11000 / duplicate key
        ↓
retry controlado

cualquier otro error
        ↓
NO retry
        ↓
propagar error original
```

No permitas:

```text
MongoDB timeout
    ↓
retry

network failure
    ↓
retry

server selection error
    ↓
retry

transaction failure
    ↓
retry
```

salvo que exista una razón explícita, segura y documentada para ese caso concreto.

### Requisitos adicionales

- No debe existir recursión indefinida.
- Debe existir un límite claro de intentos.
- Debe conservarse el error original.
- El retry debe ser determinista y controlado.
- Deben existir tests para `E11000`.
- Deben existir tests para un error MongoDB NO-E11000.
- El segundo caso debe demostrar que el error se propaga sin entrar en el retry destinado a duplicate key.

No cambies la semántica funcional del rate limiter; corrige exclusivamente su manejo de errores.

# 4. P1.2 — CORREGIR DEFINITIVAMENTE EL CICLO DE VIDA DE IDEMPOTENCY KEY

Este es un requisito crítico.

Debes auditar **todas** las Server Actions y operaciones financieras que utilicen idempotencia.

Busca especialmente patrones como:

```text
claimIdempotency()
    ↓
operación financiera
    ↓
commit
    ↓
revalidatePath / analytics / otra tarea
    ↓
error
    ↓
catch
    ↓
releaseIdempotency()
```

Este patrón NO es aceptable.

## Regla financiera

Una vez que la operación financiera haya hecho COMMIT:

> **la idempotency key queda consumida y jamás debe liberarse debido a un error posterior.**

Un error de:

- `revalidatePath`;
- analytics;
- logging no crítico;
- refresh;
- invalidación de cache;
- cualquier tarea estrictamente post-commit;

NO puede convertir una operación financiera confirmada en una operación nuevamente ejecutable.

### Debe existir separación conceptual

```text
PRE-COMMIT
    ↓
claim idempotency
    ↓
validación
    ↓
mutación financiera
    ↓
COMMIT
```

Si la operación financiera falla antes de commit:

```text
rollback
    ↓
release idempotency
```

Si el commit financiero fue exitoso:

```text
COMMIT OK
    ↓
idempotency key permanece consumida
    ↓
tareas post-commit
```

Si una tarea post-commit falla:

```text
error post-commit
    ↓
NO releaseIdempotency()
```

### IMPORTANTE

No resuelvas esto simplemente eliminando todos los `releaseIdempotency()`.

Debes distinguir correctamente:

- fallo antes de confirmar la mutación;
- fallo durante la transacción;
- fallo después del commit.

### Debes auditar TODOS los consumidores

No corrijas solamente el caso que originó el hallazgo.

Busca todas las operaciones que utilicen idempotencia, incluyendo las financieras y cualquier otra Server Action relevante.

### Test obligatorio

Debe existir una prueba equivalente a:

```text
1. claim idempotency key
2. ejecutar mutación financiera
3. commit exitoso
4. provocar error controlado post-commit
5. verificar que la idempotency key SIGUE CONSUMIDA
6. repetir la misma operación con la misma key
7. verificar que NO se vuelve a ejecutar la mutación financiera
```

Esta prueba es obligatoria para cerrar R15.3.1.

# 5. P1.3 — UNA ÚNICA DEFINICIÓN NORMATIVA DE SALDO

Este punto es obligatorio.

Audita todos los caminos que calculen balances de cuentas.

Actualmente existen conceptos equivalentes a:

```text
computeAccountLiveBalance()
```

y:

```text
accountBalancesFromMovements()
```

No debe haber dos implementaciones independientes de la semántica financiera de "saldo".

## Regla

TwinCap debe tener una única definición normativa de:

> **qué movimientos cuentan y cómo se agregan para producir el saldo.**

La optimización de consultas puede variar.

La semántica financiera NO.

### Debe garantizarse

```text
mismos movimientos válidos
        ↓
misma regla de inclusión/exclusión
        ↓
misma agregación
        ↓
mismo saldo
```

Esto incluye especialmente:

- orphan;
- ambiguous;
- unknown;
- movimientos con parents eliminados;
- workspace;
- moneda;
- signed amount;
- límites numéricos.

### No hagas esto

No soluciones el problema simplemente duplicando otra función con el mismo código.

No crees:

```text
computeAccountLiveBalance()
computeDashboardBalance()
computeTransferValidationBalance()
computeReportBalance()
```

con lógica financiera independiente.

### Arquitectura esperada

Debe existir un núcleo financiero normativo reutilizable.

La consulta del dashboard puede optimizarse para evitar N+1 o reducir round-trips, pero debe terminar utilizando la misma definición financiera.

### Requisito adicional

La agregación debe tener protección segura de números.

No debe existir un camino de saldo que pueda producir overflow silencioso mientras otro sí lo detecta.

# 6. P2 — CAS PARA updateMovement

Audita `updateMovement()`.

Si el modelo actual permite edición concurrente de Movement, debes implementar control optimista de concurrencia equivalente al estándar establecido para otras entidades financieras.

Debe existir un mecanismo del tipo:

```text
expectedVersion
        ↓
update where __v = expectedVersion
        ↓
$inc __v
```

para evitar:

```text
T1 lee v1
T2 lee v1

T1 modifica
T2 modifica

T1 guarda
T2 sobrescribe silenciosamente
```

### Especial atención

Debe proteger cambios en:

- amount;
- accountId;
- categoryId;
- fecha;
- cualquier otro campo que afecte la interpretación financiera.

### No hagas CAS innecesario

Si existe una razón técnica demostrable para que alguna operación concreta no lo necesite, documenta esa razón.

Pero no aceptes simplemente:

> "los tests pasan"

como justificación para mantener last-write-wins.

### Tests

Añade prueba concurrente de:

```text
updateMovement × updateMovement
```

y verifica que:

- una actualización gana;
- la otra detecta conflicto;
- no se pierde silenciosamente una actualización;
- no queda un estado parcialmente actualizado.

# 8. P2 — createSale: saleId Y now DENTRO DE LA TRANSACCIÓN

Según el patrón transaccional establecido en R15.3, los identificadores y timestamps de la mutación deben generarse dentro del callback de la transacción.

Normaliza:

```text
withTransaction(async session => {
    const saleId = ...
    const now = ...

    ...
})
```

No dejes:

```text
const saleId = ...
const now = ...

withTransaction(...)
```

si esto contradice el contrato vigente.

### Objetivo

Mantener un patrón transaccional coherente y evitar que datos pertenecientes a la mutación se generen fuera del contexto que finalmente la confirma.
