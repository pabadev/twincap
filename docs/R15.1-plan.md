## Fase 1 — Transaction Safety

### Hallazgo

`updateTransfer` ejecuta `Promise.all()` sobre dos `accountRepo.findById()` que comparten la misma `ClientSession`. R15 demostró que este patrón provoca `MongoServerError 251 (NoSuchTransaction → TransientTransactionError)` y retries infinitos.

|---------|--------|
| `src/core/application/transfers/update-transfer.ts` | Reemplazar `Promise.all` por lecturas secuenciales |
| `src/infrastructure/transactions/concurrency-transfers.test.ts` | Agregar test de concurrencia `updateTransfer × updateTransfer` |

### Cambio en `update-transfer.ts`

**Antes (línea 44):**

```typescript
const [sourceAccount, destinationAccount] = await Promise.all([
  accountRepo.findById(userId, existing.sourceAccountId, tx),
  accountRepo.findById(userId, existing.destinationAccountId, tx),
]);
```

**Después:**

```typescript
// Serial reads required — MongoDB driver forbids concurrent ops on same ClientSession
const sourceAccount = await accountRepo.findById(userId, existing.sourceAccountId, tx);
if (!sourceAccount) throw new NotFoundError('Source account not found');
const destinationAccount = await accountRepo.findById(userId, existing.destinationAccountId, tx);
if (!destinationAccount) throw new NotFoundError('Destination account not found');
```

Adicionar comentario explicativo consistente con `create-transfer.ts` (líneas 55-59):

```typescript
// NOTE: serial reads are REQUIRED. The MongoDB driver forbids concurrent use
// of a ClientSession: parallel ops on the same session desync the internal
// txnNumber, the server rejects them with MongoServerError 251
// (NoSuchTransaction → TransientTransactionError), and withTransaction replays
// the callback in an infinite retry loop that hangs the request.
```

### Patrón de transacción para eliminación

Cada delete root debe seguir el mismo patrón que `deleteTransfer` y `deleteSale`:

```typescript
export async function deletePayable(
  workspaceId: string,
  payableId: string,
  payableRepo: PayableRepository,
  movementRepo: MovementRepository,
  uow: UnitOfWork,
): Promise<void> {
  await uow.withTransaction(async (tx) => {
    // 1. Read aggregate inside transaction (snapshot-consistent)
    const payable = await payableRepo.findById(workspaceId, payableId);
    if (!payable) throw new NotFoundError('Payable not found');

    // 2. Delete all linked movements FIRST (R5-B order)
    const linkedMovements = await movementRepo.findByRefId(workspaceId, payableId);
    for (const movement of linkedMovements) {
      await movementRepo.delete(workspaceId, movement.id, tx);
    }

    // 3. Delete aggregate
    await payableRepo.delete(workspaceId, payableId, tx);
  });
}
```

**Orden R5-B:** movimientos primero, agregado después. Si falla entre movimientos y agregado, el agregado sobrevive con sus movimientos (estado correcto, no hay huérfanos).

### Nuevo modelo conceptual

```
Usuario introduce:
  - sourceAmount (monto que sale de la cuenta origen)
  - destinationAmount (monto que llega a la cuenta destino)

TwinCap calcula:
  - effectiveExchangeRate = destinationAmount / sourceAmount (en unidades menores)

Reglas:
  - Misma moneda: destinationAmount DEBE ser igual a sourceAmount → tasa = 1
  - Distinta moneda: ambos importes son obligatorios → tasa se deriva
  - La tasa es dato DERIVADO, nunca introducida por el usuario
  - Si destinationAmount es 0 o inválido → ValidationError
  - La tasa se almacena como dato derivado para inteligencia futura
```

### Función de dominio en `money.ts`

```typescript
/**
 * Derives the effective exchange rate from two monetary amounts.
 * The rate represents: how many units of destination currency per unit of source currency.
 *
 * Formula: effectiveRate = destinationAmount / sourceAmount
 *
 * For same-currency transfers, the rate is always 1.
 * For cross-currency, both amounts must be positive.
 * Uses integer division where possible; stores as derived value.
 *
 * @throws ValidationError if sourceAmount is zero or amounts are invalid
 */
export function deriveExchangeRate(
  source: Money,
  destination: Money,
): number {
  if (source.amount === 0) {
    throw new ValidationError('Source amount cannot be zero');
  }
  if (destination.amount === 0) {
    throw new ValidationError('Destination amount cannot be zero for cross-currency transfer');
  }
  if (source.currency === destination.currency) {
    return 1; // Same currency: rate is always 1
  }
  // Cross-currency: derive rate
  // The rate is stored as a float for display purposes but the source of truth
  // is always the two integer amounts. This value is ONLY for derived queries.
  return destination.amount / source.amount;
}
```

### 6b — Post-commit seguro

#### Hallazgo

`revalidatePath` se ejecuta después del commit financiero. Si falla, un retry podría repetir el efecto financiero.

#### Análisis actual

Revisando el código actual: `revalidatePath` se llama DESPUÉS de que el use case retorna exitosamente. El idempotency key ya previene re-registros. Por tanto, un fallo de `revalidatePath` no causa duplicación financiera — solo causa UI desactualizada temporalmente.

**Conclusión:** El patrón actual es seguro. La advertencia de la auditoría se cumple porque:
1. El commit financiero ya happened
2. El idempotency key previene re-registro
3. `revalidatePath` es best-effort (Next.js cache invalidation)

**Acción:** Documentar esta decisión en código:

```typescript
// After financial commit succeeds
// NOTE: revalidatePath is best-effort Next.js cache invalidation.
// It runs AFTER the financial commit. If it fails, the UI cache may be stale
// until the next natural revalidation, but the financial operation is already
// committed and idempotency key prevents duplicate effects on retry.
await revalidateMovementData(moduleRoute);
```

### 6c — Agregados modernos sin movimiento obligatorio

#### Hallazgo

Algunas operaciones de edición toleran que el movimiento principal no exista y continúan actualizando el agregado.

#### Acción

Para datos modernos (createdAfter = fecha de implementación R15.1), si el movimiento requerido no existe → `ConflictError` + rollback.

Para datos legacy (createdBefore) → mantener tolerancia actual con log de reconciliación.

```typescript
// En edit-principal.ts, edit-abono.ts, etc.
const movement = await movementRepo.findById(workspaceId, movementId);
if (!movement) {
  if (isModernRecord(aggregate)) {
    throw new ConflictError('Required movement not found for modern record');
  }
  // Legacy: log and continue
  logger.warn('Legacy record missing movement, continuing', { aggregateId, movementId });
}
```

### 6d — Reconciliación legacy endurecida

#### Hallazgo

El fallback legacy por `accountId + date + amount` puede producir falsos positivos.

#### Acción

```typescript
// En filter-live-linked-movements.ts, para el fallback legacy:
case 'creditReceivedPrincipal':
case 'creditGrantedPrincipal':
case 'salePayment': {
  // 1. Try exact ID match first
  const parent = await findParentByRefId(workspaceId, link.refId);
  if (parent) return true;

  // 2. Legacy fallback: value-based reconciliation
  // Only for records created before R15.1
  if (!isModernRecord(movement)) {
    const candidates = await findParentsByValue(workspaceId, kind, movement);
    if (candidates.length === 1) {
      // Unambiguous match — safe to reconcile
      return true;
    }
    if (candidates.length > 1) {
      // Ambiguous — log for manual review, but include in balance
      logger.warn('Ambiguous legacy reconciliation', {
        movementId: movement.id,
        kind,
        candidatesCount: candidates.length,
      });
      return true; // Include in balance, flag for review
    }
    // No candidates — orphan
    return false;
  }
  // Modern record with missing parent — strict
  return false;
}
```

## Invariantes formales

Después de R15.1, TwinCap declara formalmente:

| ID | Invariante | Verificación |
|----|-----------|--------------|
| I1 | **Atomicidad** — Una operación financiera confirmada produce todos sus efectos o ninguno | MongoDB Transactions + rollback tests |
| I2 | **Concurrencia** — Dos operaciones concurrentes no pueden sobrescribir silenciosamente el estado financiero de la otra | CAS `__v` + tests N=10/50/100 |
| I3 | **CAS** — Entidades versionadas usan `__v` para exclusión optimista | `runVersionedUpdate` + tests |
| I4 | **Movimientos** — Un movimiento moderno vinculado no puede existir sin su agregado propietario | `filterMovementsWithLiveParents` + tests huérfano |
| I5 | **Saldos** — Un saldo negativo es un estado financiero válido, no constituye corrupción | Tests de saldo negativo |
| I6 | **Fondos insuficientes** — La falta de saldo genera advertencia, no bloqueo automático | `InsufficientFundsWarning` + tests |
| I7 | **Transferencia multidivisa** — Importes de origen y destino son datos primarios; la tasa efectiva es derivada | `deriveExchangeRate` + tests |
| I8 | **Precisión** — Valores monetarios se almacenan y calculan sin errores de floating point | `Money` integer minor units |
| I9 | **Idempotencia** — Retry de operación crítica no duplica efecto financiero | `opId` unique index + idempotency claim |
| I10 | **Tenant isolation** — Ninguna operación modifica datos de otro tenant | `workspaceId` en todos los queries |
| I11 | **Legacy** — Compatibilidad no introduce falsos vínculos ni oculta inconsistencias ambiguas | Reconciliación legacy con detección de ambigüedad |
| I12 | **Auditabilidad** — Operación financiera explicable posteriormente | `withAudit` + `OperationLogRecord` |

## Reglas para UX/UI
