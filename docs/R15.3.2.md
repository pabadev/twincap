# R15.3.2 — CIERRE DEFINITIVO DE CONCURRENCIA FINANCIERA, SERIALIZACIÓN DE SALDOS Y CONSOLIDACIÓN DE REGLAS DEL PROYECTO

## 0. NATURALEZA DE ESTA RONDA

Esta ronda es una ronda de **corrección obligatoria y cierre técnico**, no una ronda exploratoria opcional.

El objetivo es llevar TwinCap al punto en el que pueda afirmarse con evidencia que:

1. Las operaciones financieras son atómicas.
2. Las operaciones concurrentes que afectan una misma cuenta están correctamente serializadas.
3. Ninguna operación financiera toma decisiones críticas sobre un saldo que pueda cambiar concurrentemente sin participar en el mismo mecanismo de control.
4. Las modificaciones y eliminaciones financieras protegen TODAS las cuentas afectadas.
5. No existen caminos alternativos que puedan saltarse las garantías implementadas.
6. Los tests demuestran las garantías reales y no solamente la existencia de mocks o tests unitarios superficiales.
7. Las reglas financieras y arquitectónicas del proyecto quedan documentadas en un único archivo vivo de lectura obligatoria.
8. Ese archivo se actualizará obligatoriamente cada vez que durante el desarrollo se establezca una nueva regla, restricción, decisión arquitectónica o garantía.
9. La siguiente ronda UX/UI debe poder comenzar sobre una base financiera considerada suficientemente estable.

# 6. REGLA FUNDAMENTAL DE CONCURRENCIA FINANCIERA

A partir de esta ronda debe existir una regla explícita y transversal:

> **Una operación financiera debe proteger mediante el mecanismo de concurrencia correspondiente TODA cuenta cuyo saldo pueda cambiar como consecuencia de dicha operación.**

Esto significa que debes auditar operación por operación.

No basta con preguntar:

> "¿Esta operación utiliza una transacción?"

También debes preguntar:

> "¿Qué cuentas pueden cambiar como consecuencia de esta operación?"

y:

> "¿Todas esas cuentas participan en el mismo mecanismo de serialización?"

# 8. CORRECCIÓN OBLIGATORIA — Promise.all + ClientSession

Debes eliminar cualquier uso de:

```ts
Promise.all(...)
```

que ejecute simultáneamente queries/updates usando la misma `ClientSession`.

Hallazgo concreto:

`src/infrastructure/repositories/movement-repository.ts`

`resolveDependencies()` utiliza actualmente:

```ts
Promise.all([
  CategoryModel.findOne(...).session(session ?? null),
  AccountModel.findOne(...).session(session ?? null),
])
```

Esto debe corregirse.

## Regla

Cuando exista una sesión MongoDB:

```text
operación 1
↓
operación 2
```

debe ser secuencial.

No utilices paralelismo sobre la misma `ClientSession`.

Después de corregirlo:

- buscar otros casos iguales;
- no limitarse a este archivo;
- buscar `Promise.all`;
- determinar si cada promesa utiliza una misma sesión/transacción;
- corregir todos los casos equivalentes.

# 11. CORRECCIÓN OBLIGATORIA — deleteMovement

Auditar:

`delete-movement.ts`

Eliminar un movimiento es una operación financiera porque cambia el saldo derivado.

Por tanto:

```text

```

debe:

1. identificar la cuenta afectada;
2. participar en la unidad transaccional apropiada;
3. proteger la cuenta;
4. eliminar el movimiento;
5. mantener todas las garantías existentes;
6. respetar idempotencia si corresponde al diseño actual;
7. mantener aislamiento tenant.

No aceptar:

```text
movementRepo.delete()
```

como única garantía.

# 12. CORRECCIÓN OBLIGATORIA — deleteTransfer

Auditar:

`delete-transfer.ts`

```text

+
destination account
```

La eliminación de una transferencia elimina/revierte movimientos que afectan dos cuentas.

Debe ser imposible que una operación concurrente utilice un estado de saldo que la eliminación está modificando sin participar en el mismo mecanismo de conflicto.

# 31. MATRIZ DE ATOMICIDAD + MATRIZ DE SERIALIZACIÓN

No mezclar ambos conceptos.

La documentación debe tener dos preguntas distintas:

### Atomicidad

> ¿Puede la operación quedar parcialmente aplicada?

### Serialización financiera

> ¿Puede la operación competir con otra operación que modifica el mismo saldo sin que exista un mecanismo común de conflicto?

Una operación puede ser:

```text
Atomicidad = OK
Serialización = FAIL
```

y eso debe quedar representado correctamente.

# 32. REVISIÓN DE TODOS LOS REPOSITORIES

Auditar repositories financieros para detectar:

- métodos sin session opcional;
- métodos que reciben session pero la ignoran;
- queries fuera de transaction;
- writes fuera de transaction;
- operaciones concurrentes;
- `Promise.all`;
- filtros incompletos;
- falta de workspaceId;
- versiones;
- deletes;
- updates.

Un repository que acepta:

```ts
session?: ClientSession
```

debe realmente utilizarla en TODAS las operaciones correspondientes.

---

# 33. REVISIÓN DE UNIT OF WORK

Confirmar:

```text
use case
↓
UnitOfWork
↓
transaction
↓
todos los repositories relacionados
↓
misma session
```

No aceptar una arquitectura donde:

```text
transaction
  ├── repo A usa session
  └── repo B crea/usa otra conexión/sesión
```

si ambos forman parte de la misma operación.

---

# 34. REVISIÓN DE ERRORES Y RETRIES

Auditar:

- errores de transacción;
- transient transaction errors;
- write conflicts;
- VersionError;
- duplicate key;
- idempotency conflict;
- retry.

Asegurar que un retry:

```text
NO
```

pueda producir duplicación.

Especialmente verificar:

```text
transaction retry
+
idempotency
+
post-commit
```
