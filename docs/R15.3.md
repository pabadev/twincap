# 4. P1 — SALDO INICIAL ÚNICO

## Problema

`setInitialBalance` puede crear más de un Movement de tipo `opening` porque determinadas comprobaciones de referencias excluyen deliberadamente los movimientos `opening`.

Eso no puede utilizarse como garantía para `setInitialBalance`.

Debe existir el siguiente invariante:

> Una Account puede tener cero o un Movement `opening`, pero nunca más de uno.

## Implementación obligatoria

Localiza la implementación real de:

```text
setInitialBalance
```

y crea/utiliza una comprobación específica equivalente a:

```text
findOpeningMovement(...)
```

o:

```text
countOpeningMovements(...)
```

NO reutilices ciegamente `countReferences()` si su semántica excluye `opening`.

La comprobación debe ejecutarse con las garantías transaccionales apropiadas.

Si es técnicamente viable y compatible con el modelo actual, evalúa además una restricción única apropiada en MongoDB para reforzar el invariante a nivel de persistencia.

No introduzcas un ledger nuevo.

## Tests obligatorios

Crear tests para:

1. crear Account sin opening;
2. crear opening una vez;
3. intentar crear opening nuevamente;
4. comprobar que la segunda operación falla;
5. comprobar que el saldo original permanece intacto;
6. comprobar que solamente existe un Movement `opening`;
7. ejecutar dos `setInitialBalance` concurrentes y comprobar que solamente uno puede ganar.

# 5. P1 — updateTransfer DEBE TENER CONTROL REAL DE CONCURRENCIA

Este punto es obligatorio aunque el reporte de R15.2 indique lo contrario.

Audita específicamente:

```text
src/core/application/transfers/update-transfer.ts
```

La implementación actual no puede considerarse protegida solamente porque `createTransfer` tenga CAS.

Debe impedirse el:

```text
last-write-wins
```

silencioso entre dos actualizaciones concurrentes del mismo Transfer.

## Debe existir

Un mecanismo de versionado/CAS para impedir:

```text
T1 lee Transfer v5
T2 lee Transfer v5

T1 actualiza
T2 actualiza con snapshot obsoleto

→ T2 sobrescribe silenciosamente T1
```

La operación debe detectar el conflicto.

Además, si el cambio afecta el importe de una cuenta, debe coordinarse con el mecanismo de versionado/touch utilizado para proteger el saldo.

## También debes analizar

```text
updateTransfer × createTransfer
```

porque no basta con proteger dos `updateTransfer` entre sí.

Una actualización de Transfer que modifica el saldo de una Account debe competir correctamente con otra operación financiera concurrente sobre esa misma Account.

## Criterios

Debe garantizarse:

- no lost update;
- no doble débito;
- no doble crédito;
- no Transfer/movements desincronizados;
- no bypass del control de saldo;
- conflicto detectable;
- operación atómica.

## Tests obligatorios

Ejecutar pruebas concurrentes:

```text
updateTransfer × updateTransfer
updateTransfer × createTransfer
updateTransfer × deleteTransfer
```

con múltiples iteraciones.

No basta con ejecutar dos requests una sola vez.

Utiliza concurrencia real y repite el escenario.

# 11. P1 — DEFINIR Y CORREGIR DEFINITIVAMENTE effectiveExchangeRate

Audita toda la semántica de:

```text
effectiveExchangeRate
deriveExchangeRate
Transfer
Money
currency exponent
```

Actualmente no debe asumirse que:

```text
destinationMinor / sourceMinor
```

sea una tasa económica correcta.

Ejemplo:

```text
190.000 COP
50 USD
```

Los minor units son:

```text
190000
5000
```

pero la tasa económica correcta puede ser:

```text
3.800 COP/USD
```

y no:

```text
38
```

ni:

```text
0,0263158
```

## Requisito

Define explícitamente qué significa:

```text
effectiveExchangeRate
```

Debe existir una única convención.

La tasa debe calcularse considerando los exponentes de las monedas.

Por ejemplo:

```text
destinationMajor / sourceMajor
```

o la convención inversa, pero debe quedar formalmente definida y consistente en todo el dominio.

## Prohibido

No permitas que:

```text
effectiveExchangeRate
```

sea arbitrario si el contrato establece que debe derivarse de los importes.

El dominio debe impedir inconsistencias entre:

```text
source amount
destination amount
source currency
destination currency
effectiveExchangeRate
```

## Tests obligatorios

Como mínimo:

```text
COP → USD
USD → COP
USD → USD
monedas con exponentes diferentes
```

y verificar que la tasa almacenada/derivada representa la convención definida.

# 24. INVARIANTES QUE DEBEN QUEDAR GARANTIZADOS

Al finalizar R15.3 deben ser verdaderos todos los siguientes invariantes:

### Account

- no puede existir más de un opening;
- deleteAccount no puede dejar referencias financieras válidas apuntando a la cuenta;
- operaciones concurrentes sobre saldo no pueden producir doble gasto;
- el cálculo de saldo debe ser consistente.

### Movement

- no puede apuntar a Account inexistente;
- no puede apuntar a Category inexistente;
- unknown/ambiguous links no contaminan cálculos;
- las referencias financieras modificadas concurrentemente están protegidas.

### Transfer

- source y destination movements permanecen sincronizados;
- update concurrente no produce lost update;
- saldo y Transfer se actualizan atómicamente;
- effectiveExchangeRate cumple una convención única y correcta.

### Credit / Payable

- abonos no desaparecen por actualizaciones concurrentes;
- total, paid y pending permanecen coherentes;
- CAS evita lost updates;
- operaciones de pago no pueden duplicarse silenciosamente.

### Sale

- stock y sale permanecen atómicos;
- Sale no puede quedar apuntando a Client inexistente;
- abonos y total permanecen coherentes.

### Idempotencia

- operaciones financieras no idempotentes tienen política explícita;
- retries no producen duplicados;
- índices corresponden al tenant boundary correcto.

### Reconciliation

- orphan detectable;
- ambiguous detectable;
- unknown kind detectable;
- ninguno de ellos contamina el saldo.
