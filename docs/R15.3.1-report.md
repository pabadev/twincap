## A. Resumen ejecutivo

R15.3.1 fue una **orden de implementación y corrección** (no una solicitud de
recomendaciones) sobre una base financiera ya congelada por R15.3. La ronda no
introduce funcionalidad nueva: audita, corrige defectos residuales y deja el
dominio preparado para el freeze definitivo antes de UX/UI.

**Qué se encontró y qué se corrigió:**

1. **P1.1 — Fallo crítico de retry en rate limiting**: los `catch` de
   `MongoRateLimiter` y del `MongoMonitorGuard` reintentaban ante CUALQUIER
   error de MongoDB (timeout, red, server selection, validación), no solo ante
   duplicate key. Corregido: el retry ocurre únicamente con `error.code ===
   11000`, con límite acotado (`MAX_E11000_CREATE_RETRIES = 3`) y preservando
   el error original; cualquier otro error se propaga sin reintentar.
2. **P1.2 — Ciclo de vida de idempotency key**: el patrón
   `claim → mutación → commit → tarea post-commit → error → release` existía en
   las Server Actions financieras. Corregido en las 7 capas de actions con un
   gate `committed`: la clave se libera SOLO cuando la mutación no commiteó;
   un error de revalidatePath/analytics/logging post-commit jamás rearma la
   clave. Se demostró con tests de post-commit failure contra replica set real.
3. **P1.3 — Doble semántica de saldo**: convivían dos implementaciones
   independientes del saldo de cuenta (la transaccional `computeAccountLiveBalance`
   y la del dashboard `accountBalancesFromMovements`), y esta última sumaba sin
   protección numérica. Corregido con un núcleo compartido y guardado
   (`sumSafeMinorUnits` en `money.ts`) usado por todas las agregaciones
   monetarias del sistema, incluido el dashboard y la posición financiera.
4. **P2 — CAS para `updateMovement`**: la edición de movimientos era
   last-write-wins. Implementado control optimista de concurrencia sobre `__v`
   (filtro `__v: expectedVersion` + `$inc`), con la versión del formulario,
   `ConflictError(MOVEMENT_MODIFIED_MSG)` para el perdedor y mapeo i18n.
5. **P2 — `createSale` normalizado**: `saleId` y `now` pasaron a generarse
   dentro del callback de la transacción, según el patrón vigente.
6. **P2 — Security headers de producción**: CSP con nonce por request (emitida
   desde `src/proxy.ts`, no estática), HSTS, nosniff, Referrer-Policy,
   Permissions-Policy deny-by-default y `frame-ancestors 'none'`.
7. **P2 — Matriz de concurrencia ampliada**: auditoría §10 con 13 pares
   (11 enumerados + 2 descubiertos); evidencia nueva en
   `concurrency-matrix-pairs.test.ts`; 0 cambios de código de producción.
8. **P3 — E2E de cierre**: specs nuevos de multimoneda, saldo negativo y
   opening duplicado; suite E2E completa 27/27.
9. **P3 — Documentación y semántica**: README rebrandeado a TwinCap, comentarios
   de Money corregidos, semántica de `quantity`/`stock` definida (unidades
   discretas) y documentación heredada revisada.
10. **Hallazgo no previsto (§16) — regresión del formulario de transferencia**:
    la conversión del transfer form a binding nativo React 19 (para corregir una
    carrera del patrón manual previo) rompió el flujo F5 de confirmación de
    saldo negativo de R15.1. Corregido con un enfoque híbrido que captura el
    FormData del primer submit y re-despacha la acción con el flag de
    confirmación, preservando los valores reales del usuario. Detalle completo
    en B/R-1.

La ronda cierra con todos los P0/P1 resueltos y verificados, gates de calidad
en verde (unit 1406/1406, E2E 27/27, tsc/lint/build EXIT 0) y sin
implementación de los ítems explícitamente fuera de alcance (§14).

**Causa raíz de R-1 (hallazgo crítico de la sesión final):**

- La ronda convirtió `src/app/(main)/transfers/transfer-form.tsx` a binding
  nativo React 19 (`<form action={formAction}>`) para corregir una carrera del
  patrón manual previo (el dispatch manual `preventDefault + formAction(fd)`
  se interceptaba con la transición de ruta del App Router bajo carga: el
  router abortaba la request antes de transmitirse — POST creado, `send:-1` — y
  el dialog quedaba escondido dentro del ancestro `display:none`, por lo que
  `toBeHidden` pasaba espurio). Eso arregló el E2E
  `movements-transfers.spec.ts:254` (flujo transfer normal) PERO rompió el
  flujo F5 de confirmación (`multicurrency.spec.ts:55`): el segundo submit con
  `confirmNegativeBalance=true` nunca se disparaba con binding puro nativo.
- **Root cause**: con binding nativo React 19, después de que la primera acción
  resuelve (toast warning), el formulario se AUTO-RESETEA (post-action reset de
  React 19) y un segundo submit del botón de confirmación dentro del form no
  dispara la acción (verificado en vivo: cero POSTs tras "Register anyway").
  Un intento híbrido intermedio (recoger `new FormData(formRef.current)` en el
  click de confirmación) enviaba todos los campos NO controlados vacíos
  (`sourceAccountId`, `destinationAccountId`, source/destinationAmount) → el
  servidor rechazaba con error de validación.
- **Fix aplicado**: enfoque híbrido con captura de FormData (descrito en la
  tabla, archivo `transfer-form.tsx`: `formRef` + `firstSubmitDataRef` +
  `handleConfirmNegativeBalance`). Así se preservan los valores reales del
  usuario aunque React haya reseteado el formulario.

## G. Idempotencia

Lifecycle explícito (P1.2), idéntico en las 8 operaciones de creación
financiera + las 4 de mutación adicionales protegidas (14 operaciones en 7
archivos de actions):

```text
PRE-COMMIT
   claimIdempotency(userId, action, key)   ← E11000 → duplicateRequest (retry/duplicado NO re-ejecuta)
        ↓
   validación (fechas, montos, referencias)
        ↓
   mutación financiera (uow.withTransaction…)
        ↓
   COMMIT  →  withAudit resuelto
        ↓
   committed = true
        ↓
POST-COMMIT (fuera del alcance de release)
   revalidatePath / trackAnalytics / otros best-effort
        ↓
   error post-commit  →  NO releaseIdempotency()   ★ regla P1.2
```

Reglas aplicadas:

1. **Fallo antes del commit** (validación, transacción abortada, error de
   infraestructura pre-commit) → `releaseIdempotency()` en el catch (gate
   `!committed`), el usuario puede reintentar con la misma clave.
2. **Fallo DURANTE la transacción** → rollback real; la clave se libera (gate
   `!committed`, ya que el commit point no se alcanzó).
3. **Commit exitoso** → `committed = true`; la clave queda consumida para
   siempre (TTL 24 h). Un error posterior de revalidatePath, analytics o
   logging NO rearma la clave: un retry con la misma key se responde como
   `duplicateRequest` sin re-ejecutar la mutación.
4. **Caso F5 (transferencias, R15.1)**: el warning `insufficient_funds` es
   PRE-commit por definición (cero escrituras); la acción libera la clave en la
   rama del warning, ANTES del commit point, para permitir el re-submit
   confirmado con la misma clave y el mismo form. El test dedicado de
   `transfers/idempotency-actions.test.ts` fija que esa liberación F5 es la
   ÚNICA excepción y que el flujo P1.2 la preserva.

**Test obligatorio del §21/§26**: 6 archivos `idempotency-actions.test.ts`
nuevos contra replSet real inyectan el fallo post-commit en `revalidatePath`:
1) claim, 2) mutación, 3) commit exitoso, 4) error post-commit, 5) la clave
SIGUE consumida, 6) retry con la misma key, 7) NO hay segunda mutación. Todas
las operaciones protegidas: createMovement, createTransfer, createPayable,
createSale, addAbono (payables/sales/credits), createCreditGranted,
createCreditReceived, markAsPaid, writeOffCredit, createAccount,
setInitialBalance, addSaleAbono.

## H. Saldo

**Única definición normativa** (P1.3): el saldo de una cuenta es la suma de
los `signedAmount` de los movimientos de esa cuenta en el workspace que pasan
el filtro de liveness (`filterMovementsWithLiveParents`, fail-closed), con
doble garantía:

1. **Misma regla de inclusión/exclusión**: orphan (parent eliminado), ambiguous
   y unknown-kind se EXCLUYEN (`classifyLegacyMovement`, R15.3 P4); los
   movimientos manuales y los de parents vivos se incluyen; los transfers SÍ
   mueven saldo de cuenta (la exclusión de `NON_ECONOMIC_LINK_KINDS` aplica al
   resultado ECONÓMICO, no al saldo de cuenta — semántica documentada desde
   R15.2-B).
2. **Misma agregación protegida**: Σ con `sumSafeMinorUnits` (guard
   `assertSafeMinorUnits` por paso sobre el total, rango safe-integer 2^53);
   un overflow silencioso es imposible en cualquier ruta.

Consumidores que comparten la definición:

| Consumidor | Lectura | Uso |
|---|---|---|
| `computeAccountLiveBalance` | `findByAccountIdForBalance(tx?)` (proyección mínima, session-aware) | Validación financiera DENTRO del tx: createTransfer, updateTransfer |
| `accountBalancesFromMovements` | `findByWorkspaceIdForBalance` (histórico, filtro live) | Dashboard (display); ahora con el MISMO guard numérico |

Los agregados derivados (income/expenses por categoría/contexto/mes/año,
financing flows, activos/pasivos/net de la posición financiera, totales de
venta) usan el mismo `sumSafeMinorUnits` y por lo tanto la misma política de
overflow. Se verificó con tests que las rutas que antes sumaban sin guard
(display del dashboard) ahora rechazan igual que la ruta transaccional.

La optimización de consulta puede variar (ventana del dashboard vs histórico
para el balance); la semántica financiera NO.

Política implementada (P2-d) y verificada en producción local (`next start`,
que es el entorno del E2E):

| Header / mecanismo | Valor | Dónde |
|---|---|---|
| `Content-Security-Policy` | `default-src 'self'`; `script-src 'self' 'nonce-…' 'strict-dynamic'` (+`'unsafe-eval'` solo dev); `style-src 'self' 'nonce-…'` (prod) / `'unsafe-inline'` (dev); `style-src-attr 'unsafe-inline'` (prod, atributos `style` de React — sin capacidad de ejecución); `img-src 'self' data: blob:`; `font-src 'self' data:`; `connect-src 'self'`; `object-src 'none'`; `base-uri 'self'`; `form-action 'self'`; `frame-ancestors 'none'`; `worker-src 'self'`; `upgrade-insecure-requests` (prod) | `src/proxy.ts` (`buildCspHeader`, nonce por request) |
| Nonce per-request | `crypto.randomUUID()` → base64; header `x-nonce` + CSP; aplicado al script inline de tema | `src/proxy.ts` + `src/app/layout.tsx` |
| `X-Content-Type-Options` | `nosniff` | `next.config.ts` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | `next.config.ts` |
| `Permissions-Policy` | deny-by-default: camera, microphone, geolocation, browsing-topics, payment, usb, serial, magnetometer, gyroscope, accelerometer, display-capture, xr-spatial-tracking; clipboard/fullscreen/web-share permitidos (copy y PWA intactos) | `next.config.ts` |
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains` (solo producción; `preload` omitido deliberadamente: es un compromiso permanente de una vía) | `next.config.ts` |

transporta un nonce por request (emitida en `proxy.ts`, antes del render, según
la guía oficial de Next.js); el matcher del proxy excluye los prefetches de RSC
(no son documentos y no necesitan CSP/nonce); la CSP dev vs prod difiere por el
tooling de desarrollo (React DevTools/Turbopack HMR inyectan `<style>`).

funcionan bajo la política activa). Ningún header se agregó "para marcar
